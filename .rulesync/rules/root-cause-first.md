# 根本原因を先に：調査・修正・エスカレーション

このファイルは CLAUDE.md の「必ず守ること」2・6 の詳細。バグ修正、テスト失敗、想定外の挙動に取りかかるときに従う。

## 1. 手順

1. **grilling**：実装前に grilling スキルで質問ツリーを出し、推奨回答で自分で埋める。Q&A は作業 issue に `Claude Code:` で始まるコメントとして残す。推奨回答で決めきれない分かれ道があれば、ここで stopped にして止まる。
2. **調査**（`.claude/skills/systematic-debugging/`）：直す前に次の4つを書き出す。
   - 現象：何が起きているか。エラー本文、ログ、再現した出力
   - 再現条件：どの入力・環境・手順で起きるか
   - 根本原因の仮説と検証結果：仮説ごとに、何を見て確かめ、どうなったか
   - 影響範囲：原因の部品を使っている呼び出し元・利用箇所
3. **失敗するテスト**（`.claude/skills/test-driven-development/`）：原因を再現するテストを書き、修正前に失敗することを確かめる。
4. **修正**：原因がある層を直す（2 を参照）。
5. **完了前の検証**（3 を参照）。

## 2. どこを直すか

- 原因が共通部品、API 契約、データモデル、責務の分け方にあるなら、その層を直す。呼び出し元ごとに補正を足さない。直した層の利用箇所をすべて調べ、影響を PR に書く。
- 原因が局所的なら局所修正でよい。「根本修正」は無関係なコードの全面書き換えではない。原因をなくすのに必要な最小限の設計変更を選ぶ。
- 修正が広い範囲に及ぶ場合は、不要な大改修を避けたうえで、範囲を PR と stopped／done コメントに書いてリーダー bot に知らせる。
- 修正を3回試しても直らないときは、それ以上パッチを重ねない。設計の前提を疑い、調べた内容を書いて止まる。

## 3. 禁止パターン（症状隠し）

| パターン | 例 | 代わりにやること |
|---|---|---|
| 不要な特殊分岐 | 特定の ID や入力だけ `if` で除外する | その入力で壊れる原因を直す |
| 例外の握りつぶし | 空の `catch {}`、`catch` してログだけ出して続行 | 起きる原因を直す。扱うなら呼び出し側に意味のある結果を返す |
| 過剰なガード | 起きないはずの `null` チェックを各所に足す | 不正な値が入る入口を直し、型で表す |
| 恣意的なリトライ・待ち時間 | 根拠なく `retry(3)`、`sleep(500)` を足す | 待つ条件を特定して条件で待つ |
| 呼び出し側ごとの重複補正 | 同じ変換を利用箇所ごとに書く | 補正の原因になっている部品を直す |
| テストの弱体化 | 期待値を緩める、テストを skip する | 失敗の原因を直す |

スキル `systematic-debugging` の `defense-in-depth.md` は「各層で検証する」ことを勧めるが、このリポジトリでは過剰なガードを禁止しているほうを優先する。入口での検証と型で不正な状態を防ぎ、各層に同じチェックを重ねない。`condition-based-waiting.md` が勧める「理由のコメント」は、`EXTERNAL:` などのマーカー付き制約コメントとして書く。

## 4. 一時回避とエスカレーション

- 外部の制約（ブラウザ・ストア・外部 API・依存ライブラリの不具合など）で恒久修正ができないときは、まず恒久修正ができないことを確かめる（上流の issue、仕様、再現結果）。
- それでも一時回避が要るなら、黙って入れない。作業 issue に stopped コメント（`Claude Code:` で始める）で、制約の内容・出典・回避案・恒久修正の条件を書いて止まる。担当 bot がリーダー bot と kyto に上げる。
- 許可されて入れる回避策には、`EXTERNAL: <制約と出典>` の制約コメントを付け、恒久修正の issue を作って PR に書く。

## 5. 完了前の検証

「直った」「通った」と書く前に、次を実際に実行して確かめる。

- 追加した回帰テストが修正前に失敗し、修正後に通ること
- 関連テストとリポジトリの全テスト、静的解析、コメント検査が通ること
- 元の現象が再現しなくなったこと（再現手順を実行した結果）

実行したコマンドと結果を PR の「テスト・静的解析・コメント検査結果」に書く。実行できなかったものは理由を書き、通ったことにしない。

## 6. レビューで確かめられること

リーダー bot は PR を次の観点で受け入れ判定する。PR 本文はこれに答えられるように書く。

- 症状と根本原因の説明がある（バグ修正の場合）
- 修正が原因のある箇所に対応している
- 不要な特殊分岐・エラー隠し・ワークアラウンドがない
- コメント規約を満たし、例外には根拠がある
- テストの追加・更新がある、または非適用の理由が妥当
- テスト・静的解析・コメント検査の必須 CI が成功している
- 既存の API 契約・挙動・セキュリティ・互換性への影響を確かめている
