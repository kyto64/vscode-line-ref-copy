# コード品質：コメント・テスト・静的解析

このファイルは CLAUDE.md の「必ず守ること」1・3・4・5 の詳細。判断に迷ったら、ここに書いた禁止パターンと例外の条件で決める。

## 1. コメント規約（原則禁止）

### 1.1 禁止するコメント

PR で追加・変更するコメントのうち、次に当たるものは書かない。CI のコメント検査が違反として落とす。

| 種類 | 例 | 代わりにやること |
|---|---|---|
| 何をしているかの説明 | `// ユーザー一覧を取得する` | 関数名・変数名で表す（`fetchUsers()`） |
| 処理手順の言い換え | `// 1. 入力を検証 2. 保存` | 手順ごとに関数を抽出する |
| 変更履歴・経緯 | `// 2026-11 に #123 で修正` | コミットメッセージと PR に書く |
| 修正理由の言い訳 | `// ここで null が来ることがあるので` | null が来る原因を直す。型で表す |
| 先送り | `// TODO: あとで直す`、`FIXME`、`HACK`、`XXX` | いま直すか、issue を作る |
| ワークアラウンドの正当化 | `// 暫定対応。一時的にリトライする` | 根本原因を直す。無理ならエスカレーション |
| 検査の無効化 | `// eslint-disable-next-line`、`@ts-ignore`、`# noqa` | 指摘の原因を直す |
| コメントアウトしたコード | `// oldFunction();` | 消す。履歴は git にある |

### 1.2 許す例外

例外を使ったら、PR 本文の「コメント例外」にその場所と理由を書く。CI はこれらを「許可した例外」として一覧に出し、リーダー bot がレビューする。

| 例外 | 書き方 | 条件 |
|---|---|---|
| 著作権・ライセンス表記 | `// SPDX-License-Identifier: MIT`、`Copyright ...` | 法的に必要なもの |
| 公開 API／ツールのドキュメント | エクスポートした宣言の直前の `/** ... */`（JSDoc／TSDoc）、Python の公開関数・クラスの docstring | 外部から使われる契約を説明するもの。中身の実装手順は書かない |
| コードで表せない制約 | `// INVARIANT: <理由>`、`// SECURITY: <理由>`、`// EXTERNAL: <理由と仕様の出典>` | 非自明な不変条件、セキュリティ上の制約、外部仕様（ブラウザ・ストア・API など）の制約。理由は 8 文字以上 |
| ツール向けの指示 | `/// <reference ...>`、`/* @vite-ignore */`、`/*#__PURE__*/`、`prettier-ignore`、shebang | ビルド・実行に必要なもの |
| 生成コード | `@generated`、`DO NOT EDIT` のヘッダ | 生成元を直す |
| SHA 固定した Action のバージョン | `uses: owner/action@<40桁SHA> # v1.2.3` | gh-actions-lock や Dependabot が付けるもの |

- 例外のコメントは英語で書く（このリポジトリの言語ポリシー：`docs/development/language-policy.md`）。
- 制約コメントは、同じ内容を名前・型・テスト・アサーションで表せないことを確かめてから書く。表せるならコードで表す。
- 連続した行コメントは1つのブロックとして扱う。マーカーはブロックの先頭行に書く。
- 検査の無効化がどうしても要るときは、同じコメントに `-- EXTERNAL: <理由>` などの理由を書く。CI は通すが、必ずリーダー bot のレビュー対象になる。理由のない無効化は違反。

### 1.3 既存コメントの扱い

- 既存のコメントを一律に消さない。変更する箇所に関係する不要なコメントだけ整理する。
- 公開契約・必須表記・意味のある制約は壊さない。残す制約コメントにマーカーがなければ、触るついでにマーカーを付けてよい。
- 文面を変えずに移動しただけのコメントは、CI の検査対象にならない。
- コメント規約を満たすために、意味のない関数分割や不自然な命名をしない。

## 2. テスト

### 2.1 書くテスト

- バグ修正：修正前に失敗する回帰テストを先に書き、失敗することを確かめてから直す。自動テストが不可能なら、その理由と代わりに行った確認を PR に書く。
- 新機能：要件に見合うテストを書く。正常系だけでなく、重要な境界と異常系も確かめる。
- テストは挙動を確かめる。定数の値や文言、内部構造そのものを固定するだけのテストは書かない。

### 2.2 禁止すること

- テストを通すためだけに期待値を緩める、アサーションを消す、テストを消す
- `.skip` / `.only` / `xit` / `@pytest.mark.skip` などでテストを外したままにする
- lint・型検査・コメント検査を無効化する、設定で対象から外す、閾値やカバレッジ基準を下げる
- CI のジョブやステップを外す、`continue-on-error` で失敗を隠す
- テスト失敗を「非適用」と言い換える

### 2.3 テストが非適用のとき

ドキュメントだけの変更などテストが成り立たない変更では、どのジョブを非適用にしたかと理由を PR に書く。非適用の判定は CI の設定（パスフィルタなど）で追跡できるようにし、セッションの判断だけで省かない。

## 3. 静的解析とコメント検査

- このリポジトリの lint・型検査（またはコンパイル）を実行し、失敗をすべて直してから PR を出す。
- コメント検査は CI の `comment-check` ジョブが、PR で追加・変更したコメントだけを言語別のパーサで調べる。ローカルでは次で同じ検査ができる。

```bash
node .github/comment-check/src/cli.mjs --base origin/master
```

- 結果はコマンドと終了コードごと PR に書く。走らなかったものは「未実行」と理由を書く。

## 4. このリポジトリのコマンド

CI（`.github/workflows/ci.yml`）と同じコマンド。PR を出す前にすべて実行する。

| 種類 | コマンド | CI のジョブ |
|---|---|---|
| 依存の導入 | `npm ci` | `build` |
| 型検査・コンパイル | `npm run compile`（`tsc -p ./`） | `build` |
| lint | `npm run lint`（oxlint、設定は `.oxlintrc.json`） | `build` |
| テスト | `xvfb-run -a npm test`（Linux 以外は `npm test`） | `build` |
| コメント検査 | `npm ci --prefix .github/comment-check --ignore-scripts` のあと `node .github/comment-check/src/cli.mjs --base origin/master` | `comment-check` |
| コメント検査器自身のテスト | `npm test --prefix .github/comment-check`（シェルの検査に shfmt v3.14.1 が要る。パスは `COMMENT_CHECK_SHFMT`） | `comment-check` |
| rulesync の生成物 | `npm run rules:generate` のあと差分がないこと | `check-rulesync` |
